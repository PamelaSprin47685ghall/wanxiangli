# 构建与交付

## AXIOM
1. [开发者] 修改一个库时，不应编译其他库，也不应先安装 .NET。
   - 理由：维护成本包括等待验证的时间。
2. [使用者] npm 包必须在没有本仓源码、旧仓和编译器的目录中使用。
   - 理由：只有真实安装能证明它已经是库。

## LEMMA
1. [AXIOM 1] 每个已实现子模块一个显式 fsproj；直接调用 npm Fable 编译器，不建立第二份源文件清单。组合通过公开 ESM 入口使用参与者，构建不内联兄弟库。
   - 推理：工程文件已经是编译输入的唯一清单。
2. [AXIOM 2] 交付验收使用实际 tarball，不用 workspace link、NODE_PATH 或源码回退。
   - 推理：链接会掩盖遗漏文件和反向依赖。
3. [AXIOM 2; LEMMA 1] 公开入口由已实现模块推出：每个带 fsproj 的模块恰好一个 exports 项，指向 build 脚本产出的入口文件，类型声明在 files 白名单里；没有指向不存在模块的入口。
   - 推理：多人并行加模块时，exports、files 与 fsproj 是三处手写清单；任何一处漏写，开发期 `file:` 链接仍能用，安装包却缺文件或缺类型。
4. [AXIOM 1; LEMMA 1] 构建按模块增量：模块的编译输入是 fsproj 文本、其显式源文件、Node 身份、scripts 下的构建模块以及已安装 Fable、FCS、元数据、运行库、esbuild 及其当前依赖的实际内容。包清单和锁文件同样参与摘要，不仅比较版本号。输入摘要未变、且 `dist/<name>` 与记录的逐文件摘要一致时跳过该模块；`--force` 或 `WANXIANGLI_BUILD_FORCE=1` 强制重编选中范围。产物不得含进程号等非输入信息，同样输入得到同样字节。
   - 推理：fsproj 已是唯一输入清单，摘要可以完整覆盖它；产物逐文件核对使被改动或被换掉的 dist 不会被误认成缓存。摘要记录在 `.build-stamps/`，仅在产物原子替换成功后写入。
5. [AXIOM 1; LEMMA 1, 4] 输入清单按 Fable 的属性读取规则处理属性顺序、引号、空白与 XML 注释。构建开始时记录选中模块的输入，发布各模块前和整次构建结束前复查；缓存命中的模块也必须复查。输入改变或不可读时构建失败，失效模块的摘要不保留；下次按模块补编，不自动转为全库强制重编。
   - 推理：编译器实际读取的源码不能漏出缓存判断；构建期间保存文件时，成功结果不能指向已经过时的输入。全库构建还需复查模块清单，显式选中模块的构建只约束其选中范围。
6. [AXIOM 1; LEMMA 1, 4, 5] 统一由 `node scripts/build.mjs` 或 `npm run build` 连接工作树的常驻服务。请求顺序执行，checker 按引用名称、DLL 内容和选项复用；每个项目解析前和输出后调用公开 ClearCache。默认 worker 累计完成 128 个项目后在构建边界退出，服务空闲十分钟退出。失败丢弃 worker；工具链内容改变替换 worker，构建代码或 Node 身份改变重启服务。全命中缓存不启动 worker，异步输出失败必须使构建失败。
   - 推理：重复初始化也是局部修改的等待成本；清项目缓存与限制 worker 寿命分别处理旧项目状态和长期累积。初始化可以跨命令共享，项目检查结果仍须从本轮输入重新取得。寿命阈值不冒充字节上限。
7. [AXIOM 1; LEMMA 5, 6] 每个真实工作树只有一个发布者。完整归属目录通过原子改名取得，归属包含 PID、启动时间和随机代号；退出和故障接管把旧归属移入不能覆盖的非空旧代目录。编译 worker 只写临时产物，服务确认输入和归属后才发布；客户端断开不把未知结果转成成功。
   - 推理：单靠 PID 或删除锁文件，会在 PID 重用或迟到的清理请求中误认新服务。保留旧代记录可使同一次旧接管重复执行仍不触及新归属；不同工作树使用各自的归属和通信端点。

此条约束独立发行验收，不禁止宿主在开发期通过 submodule 和 `file:wanxiangli` 消费源码依赖。任何打包所得 `.tgz` 都只能是临时构建产物，永远不得进入 Git。开发接线的通过不能代替发行包验收。

9. [LEMMA 4] 未改动的模块不重编，改动的模块重编，篡改过的产物重编，`--force` 全部重编；缓存产物与强制重编产物逐字节相同。
   - 证明：`tests/build.test.mjs` 的 SPEC[build-002]：未改动跳过、改源码重编、改回再重编、篡改产物重编、`--force` 全部重编，缓存产物与冷构建、强制重编逐字节相同。
10. [LEMMA 5] WHAT[build-010] 不同合法属性写法的源码改动均触发重编；构建期间保存源码、修改工程或构建脚本、删除源码、添加模块不得误报成功。源码在编译期间改变时不覆盖上一份产物，失败后的普通增量重试只补编失效模块。
    - 证明：2026-10-23，Node 26.6.0 / Fable CLI 3.8.1 下 `tests/010.test.mjs` 的 14 个案例通过，包含两个构建脚本的修改检测。使用真实 Fable 编译和新 Node 进程执行产物；文件改动固定在缓存检查、FCS 解析完成和产物发布边界，不依靠定时碰运气。另通过原有 12 个相关构建案例与 3 个公开入口检查；51 模块全量构建成功，无改动重复构建全部命中缓存，产物内容及修改时间不变。
11. [LEMMA 6] WHAT[build-011] 同进程复用的输出和执行结果与每次独立启动的 Fable 相同。删除源文件、调整文件顺序、修改签名、切换同名项目、改变条件编译或告警选项、替换同名 DLL 不得沿用旧状态。输出错误不得发布半成品，普通增量重试仍只编译失效模块。
    - 证明：2026-10-23，`tests/011.test.mjs` 的 5 个案例通过，其中 21 组输入与独立 Fable CLI 对照，核对成功或失败、输出字节和成功产物的实际执行结果；另覆盖写文件失败、Fable 输出阶段报错、增量恢复和编译入口改动后的失效。10 次相同配置的项目检查只创建 1 个 checker，每次解析前均清理缓存；不同选项和同名不同内容的 DLL 分别使用独立 checker。
    - 性能验收：Apple M3 Pro / Node 26.6.0 / Fable CLI 3.8.1，同一批 51 模块，每次构建启动新进程。全量 67.242 → 11.586 秒，FCS 合计 46.339 → 6.386 秒；5 模块增量 6.689 → 2.657 秒；无改动 0.097 → 0.090 秒。单模块各测 3 次，中位数 1.327 → 1.304 秒，其余为单次对照。所有轮次的 51 个产物逐字节一致，缓存模块的内容和修改时间不变，构建进程全部退出。全量进程树 RSS 峰值 586.9 → 629.0 MiB，macOS 物理占用峰值 559.7 → 759.2 MiB；本方案消除跨构建保留状态，不承诺降低单次构建的内存峰值。

## 常驻构建用法

运行 `npm run build`，或 `npm run build -- module-name` 构建指定模块。独立命令会复用本工作树的 checker；多个调用按顺序执行，并在执行时重新读取输入。未变模块保留产物。

`npm run build -- --status` 查询服务；`npm run build -- --stop` 等待当前请求结束并退出。查询不会启动服务。停止后全缓存构建不加载 checker。

每个项目解析前清理项目缓存。worker 默认累计 128 个项目后在构建边界退出，服务默认空闲十分钟退出；需要时由下一次构建重新启动。不同工作树互不共享服务。

输入或工具链变化会使相应缓存失效。编译错误或进程中断以非零退出码报告；修复后重跑普通构建即可。跨模块发布发生 I/O 错误时，部分模块可能已更新，失败结果不能用于发布。参数和测试记录见 `BUILDING.txt`。
