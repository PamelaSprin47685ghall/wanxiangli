# scope-progress — 作用域进度与顾问协作

独立 npm 入口：`wanxiangli/scope-progress`。在总流程中，本包负责管理任务作用域（Scope）的计费回合进度、估计衰减判定，并在进度停滞或耗尽时触发顾问咨询协作，确保长程任务持续可控、不盲目空耗。

## 状态所有权
- **ScopeProgress** 独占管理会话与作用域的回合计费、剩余估计（`remainingScopeTurnsEstimate`）及 `ResetDue` 状态。
- **AdvisorFlow** 独占持有四段式顾问咨询的状态机、单飞互斥队列与阶段持久化记录。
- 本包不直接解析 HTTP/SDK 包络，不负责底层消息网络传输，不持有通用工作规则。

## AXIOM
1. 工作模型在一次工具调用里报告当前 Scope 的剩余计费回合数，值是非负实数（允许小数）；宿主把该次调用转交本库，本库不认识也不依赖具体工具名。一个 Provider 回合只计一次，同一回合多个报告取最小值，没有有效报告则不计费。
2. 每个计费回合的估计应比上一计费回合至少下降 0.1；判定用 0.08 的实数门槛（`JudgedDrop`），对外文案只写 0.1（`DocumentedDrop`），使按承诺报数不会被十进制表示误差误判。降幅不足（含持平与上升）或已报告零仍继续计费时请求顾问咨询。估计为零则保留 ResetDue 直到新的真实 Scope 开始。不分析模型动机，也不建立隐含缺报惩罚。
3. Advisor Process 是同一 Session 一次只运行一份的四段协作。工作者临时问询与持续顾问席位是不同的物理会话；库只要求明确的问答与投递端口。

## LEMMA
1. 每项报告绑定 `sessionId + scopeId + providerRunId + toolCallId`。同一 Provider 回合结算一次，同身份内容冲突明确拒绝；内存与持久模式都将同一 Scope 的物理 toolCallId 绑定原 Provider 回合，改用新的内部 runId 重放不能再计费。
2. Scope 标识仅随成功提交的 `ScopeReanchored` 改变；压缩、任期变化及代理消息不重置进度基线。
3. 运行中的咨询最多合并一项等待咨询，触发身份完整保留；阶段严格按 A→B→C→D 执行，前序失败则后续不得执行。
4. 四段问询在启动时固定语言（`en` 或 `zh-CN`），向模型呈现自然语言问题，不泄露内部进程与存储细节。
5. 结果未知时不自动盲目重发外部调用；持久化记录只有在提交确认后才释放内存锁。

## SPEC（操作员与调用方流程）

1. **回合计费与进度判定**：
   - 宿主把模型报告的估计值连同该次调用的 `providerRunId` 与 `toolCallId` 传入 `record`。同一物理回合多次调用取最小值。
   - 若估计值较上一回合降幅达到门槛（>= 0.08），计费成功推进；
   - 若降幅不足、数值上升或持平，系统判定为停滞并触发顾问咨询流程；
   - 若估计值为 0，进入 `ResetDue` 状态，后续必须执行 `resetScope`。
2. **顾问问询四段流程**：
   - 触发咨询时，系统通过 `AdvisorFlow` 依次发起四段问答（A→B→C→D），并使用会话所选语言向顾问呈现问题。
   - 完成后将答复提炼为强指导（steer）交还主流程；若阶段中断或调用失败，如实报告并不跳级执行。
3. **崩溃恢复与持久化**：
   - 咨询状态通过 SQLite 持久化日志安全落盘。进程重启或强杀恢复时，已确认阶段直接复用，未决报告按次序认领，绝不重复扣费或重复发起外部调用。
