# eventstore — 原子追加日志

层：SQLite 运行时库。独立 npm 入口 `wanxiangli/eventstore`。在总流程中，本模块把任务状态和领域事件写进 SQLite 原子追加日志：提交成功的事实在进程被杀后仍能按流完整读回，两个写入者不能各自赢得同一修订号。

## 状态所有权
- 本模块独占拥有基于 SQLite 的事件追加协议（`BEGIN IMMEDIATE`、期望修订号核验、`synchronous=FULL`）。
- 模块不自建文件锁、不造私有存储引擎，不拥有领域事件词汇，仅存储不透明 UTF-8/BLOB 载荷。

## AXIOM
1. [使用者] 成功提交的事实在进程被杀后仍能读回，两个写入者不能各自赢得同一修订号。
   - 理由：工作唯一性和崩溃恢复都依赖这件事。
2. [开发者] 不为首个真实使用方自写数据库、文件锁、段滚动和修复器。
   - 理由：自造底层存储会重新制造维护负担。
3. [使用者] Node 与 Bun 使用同一份日志规则，不因运行时不同维护两套实现。

## LEMMA
1. [AXIOM 1, 2] SQLite 事务承载一整笔不透明 UTF-8 文本；同流按修订号递增，追加前比较期望修订号。
2. [AXIOM 1] 同流同 requestId 仅允许相同 body；冲突零追加；未知提交保持 Unknown。
3. [AXIOM 1] 历史只追加，读回核对连续性与内容哈希；禁止原地 UPDATE/DELETE。
4. [AXIOM 2, 3] 统一基于标准 SQLite API（exec, prepare, close），在 Node 与 Bun 环境下行为一致。

## SPEC（调用方流程）

1. **原子追加与提交确认**：
   - 传入期望修订号与事件载荷调用 `append`。系统在事务中比对修订号并插入；COMMIT 成功返回 `Committed`；修订号或 requestId 对不上返回 `Conflict`，不写入。
2. **幂等重放**：
   - 相同 requestId 再次提交相同内容时，返回 `Replayed`，不重复写入第二笔记录。
3. **未知提交与连接关闭**：
   - COMMIT 阶段发生未知异常时，返回 `Unknown` 并关闭当前数据库连接；之后的调用直接报错，须重开连接，避免在不确定的落盘状态下继续追加。
