# Fission

遵守库根《万象理》。入口 `wanxiangli/fission-group`。这是同一参与者分道执行、汇合后继续完成原任务的完整职责，不是若干独立小包。

## AXIOM

1. 用户需要参与者把事情做成。分道是内部工作方式，不能把某条道停下或一条发送回执当成整体完成。
2. 已经产生的道、送达和材料必须保留各自结果。部分启动失败不是没有启动；失败、未知和已确认完成不能互换。
3. 道的次序在准入时确定。重复事实可以重放，异值不能覆盖旧事实；最终汇合的顺序不取决于完成先后。

## LEMMA

`FissionHistory` 组合已有规则，独占不可变组历史、活跃/最近组和道索引；调用方持有一个历史值，通过 `apply` 取得下一值。读取返回视图，不产生第二份权威。`FissionRuntime` 继续持有进程内资源、发送与接管认领、静默替换标记；`FissionAdmissionRegistry` 持有准入预留。它们各自的状态不复制到宿主。

`FissionLifecycle` 编排这些对象与材料存储、发送、完成发布等参与者。它负责创建—登记—逐道启动—替换原执行的次序、失败后的逐道清理、共享完成广播、材料汇合、接管和终结。组合者没有假定中断回执就证明物理执行结束。

具体宿主的事件解释、空闲许可、请求形状、提示渲染和终结发布协议留在适配层。适配层交付已解释的事实和操作结果；库不导入宿主 SDK，不解释具体 hook 次序。日志提交幂等不等于发送或进程启动幂等。

## SPEC

操作者请求分道后，系统保留原责任和道输入，创建各道并登记组，再依次启动。只有各道启动成功才请求替换原执行。任何普通失败按已经创建的道清理；先前已登记的组不会被伪装成不存在。

道提交的工作和分道前已在途的结果汇合后，最终一道取得整组材料，继续完成同一任务。只有最终报告发布成功，组才记为收束并释放资源。无交付的停顿保留未完成责任，发送被拒或结果未确认不会被当成已送达。

宿主程序仍负责实际创建、中断和发送；库只持有中立历史及协作顺序。相关改变用就近行为测试和安装消费者检查；测试结果留在具体工作记录。
