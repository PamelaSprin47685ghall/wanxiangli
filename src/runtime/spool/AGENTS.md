# spool — 有界内存与完整输出外存

层：物理能力库。入口 `wanxiangli/spool`，对象 `OutputSpool`。只使用 `node:fs`、`node:path`、`node:crypto`；不导入进程、宿主、Work、Journal 或兄弟库。它不启动进程，也不决定输出预算——这两件事属于调用它的组合者。

## AXIOM
1. [使用者] 需要完整输出时，本对象交出的每一个字节都与观察到的原始字节相同，顺序与到达顺序相同；不能把留尾说成完整。
   - 理由：外存只有在可以完整重读时才有意义；丢字节而报完整会让调用方基于错误材料继续工作。
2. [使用者、开发者] 内存只持有显式上限内的字节；超过上限后全部字节转入一个文件，内存不再积压。
   - 理由：长命令可能产生任意多输出，常驻内存会拖垮整个宿主。
3. [使用者] 外存失败必须如实说出：失败的动作、真实错误码、已写入多少字节。
   - 理由：磁盘满、目录权限和文件大小限制都是真实环境；把失败吞成异常或成功，调用方无从判断结果是否可用。

## LEMMA
1. [AXIOM 1, 2] `append(channel, bytes)` 复制输入。累计未超过 `memoryBytes` 时两路分别留在内存；第一次超过时，按到达顺序把已持有的全部字节写入 `directory` 下新建的独占文件（`wx`、0600），此后直接追加。文件是合并流，不保留两路边界。
   - 推理：在切换点之前，两路分离的结果足够小，可以直接交回；切换后只能保证到达顺序，不能虚构两路的真实因果顺序。
2. [AXIOM 3] 打开或写入失败后进入 `Failed`：释放内存，关闭文件，之后只计数，不再写入，不重试。`written` 是内核确认写入的字节数，部分写入也逐次计入。
   - 推理：重试会把同一字节写两次，或在未知位置之后续写；只计数让调用方知道丢了多少。
3. [AXIOM 1] `finish()` 只封口一次，结果可以重复取得且每次返回副本；之后的 `append` 返回 `Finished`，不计数也不写入——进程超时或取消后仍可能有迟到输出，它们不属于已封口的结果。`discard()` 只删除本实例自己创建的文件，重复调用返回 `Absent`。
   - 推理：结果所有权交给调用方后，内部字节不能再被外部修改；物理回收只针对确切实例，不按路径猜测别人的文件。
4. [AXIOM 1] `OutputSpool.readChunks(path, chunkBytes, consume)` 按不超过 `chunkBytes` 的块读出完整文件；`OutputSpool.readTail(path, limitBytes)` 只读文件末尾 `limitBytes`，切口最多跳过三个 UTF-8 续字节，报告 `discarded`。
   - 推理：尾部是明确区间的原始字节，不是改写过的文本；二进制输出不会因对齐而被大段吞掉。

## SPEC
1. [LEMMA 1, 3] 非法选项、通道和字节在创建任何文件前拒绝；内存模式两路逐字节准确、输入输出不共享别名、多实例隔离。
   - 证明：`tests/001.test.mjs`。
2. [LEMMA 1] 跨过上限时，已持有字节与后续字节按到达顺序进入同一文件；10 MiB 分块输出期间 `held` 不超过上限；真实子进程的 3 MiB 输出及非法 UTF-8 字节经 SHA-256 比对一致。
   - 证明：`tests/002.test.mjs`。只测了 `held` 计数，未测量整个进程 RSS。
3. [LEMMA 2] 目录拒绝写入（EACCES）、目录被删除（ENOENT）、内核文件大小限制导致中途 EFBIG：均返回 `Failed`，错误码为真实值，`written` 等于文件实际大小。
   - 证明：`tests/003.test.mjs`。EFBIG 由 `ulimit -f` 在独立子进程中产生，不是测试自抛异常。以 root 运行时权限用例跳过并注明原因。
4. [LEMMA 4] 分块重读完整、尾部 UTF-8 对齐与 `discarded` 精确、二进制尾部最多跳过三字节、缺失文件返回 ENOENT。
   - 证明：`tests/004.test.mjs`。

## 边界

- 这是单进程内的同步写入者。没有 fsync，不承诺掉电后持久；没有跨进程锁，也不做保留期清理——谁取得结果谁负责 `discard` 或继续持有。
- 本库不判断输出预算、截断说明或面向模型的总字节预算；那是组合者用 `readTail` 的结果去做的事。
- Linux 实测；macOS 采用同一 API 但未单独验证；Windows 未验证，不作支持声明。
