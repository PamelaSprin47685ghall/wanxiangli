# dispatch

公开入口是 `wanxiangli/dispatch`。系统把下一步指令交给执行者时，需要区分已发出回执、已被物理接收、明确未发送和结果未知，避免同一指令重复执行。宿主消息形状、发送 SDK、终端事件翻译及诊断文案属于外层适配。

## 状态与分工

`Dispatch` 保存认领规则，不持有投影、日志或发送句柄。它计算认领键的原文、序号作用域、认领与结算后的编辑，以及发送回答对应的账本动作。调用方负责哈希、持久化和应用编辑。Submit 只记回执；Accept 才移出待决并记物理接收；Abandon 移出待决，但不抹去已经存在的精确物理接收记录。

`DeliveryAttemptLedger` 持有进程内交付记录，以 session、providerRun、callId 区分一次交付的成立、呈现和中断。物理围栏不被后来的登记改写。中断任务是不透明句柄，仍由调用方等待；同一运行的多个任务按登记次序选最新一项。生产按会话删除记录，不用全量清空代替会话退场。持久记录是另一路输入，查不到不等于此前没有交付。

`PromptPhysicalAcceptance` 是确认回调和等待者的唯一 owner。`accepted` 与 `cancel` 先取走本 key 的记录，再通知或结算；重复通知不重复完成。注册与等待返回的租约只移除自己，不误删后来覆盖的注册或同 key 的其他等待者。确认预算优先用正数入参，否则沿现有环境变量和 10000ms 默认值。

`DispatchAttempt` 组合发送效果、上述确认对象和认领规则。实例可并行接受多次调用，每次调用仅持有自己的终端订阅、注册、确认等待与迟到回调。组装方必须注入现有确认对象；本对象不建第二份待决表，不认领新工作，也不复制 durable 日志。

## 一次派发

1. 外层完成 durable 认领、准备本次载荷，然后调用 `sendInitial` 或 `sendContinuation`。对象先订阅终端结果，再注册物理确认；确认租约交给调用方的生命周期 owner。
2. 续接发送在最后一次同步 `admit` 成功后立即调用 `send`，二者之间不等待 Promise。外层发送回调也必须先发起真实发送，再异步转换结果。准入不通过时先释放注册，再按 superseded 放弃认领；放弃失败覆盖原拒绝，成功则保留原拒绝对象。
3. 等待模式收到普通回执时先记 Submitted，有确认观察者才等待物理确认；收到物理消息 id 时先记 Submitted，再记 PhysicalAccepted。明确拒绝走 Abandon；结果未知不写新的派发事实、不重发，也不伪称确定未发送。
4. Detached 模式先发起发送，再记本地回执，随后返回；它不等待发送 Promise 完成。发送 Promise 的结局与独立迟到通知分别处理，不增设另一把一次性结算锁。未知只报告待决；后来的明确拒绝仍可走放弃。明确拒绝和未知都会通知失败观察者，观察者异常转为诊断。

初次发送与续接发送保留各自的现行错误边界。初次 Detached 的回执持久化失败保留注册；续接同类失败释放注册。普通 Result 错误和 Promise 拒绝不互相替换：明确拒绝后的 Abandon 普通错误仍返回原发送理由，Abandon 拒绝则按异常答复。订阅与租约释放的异常仍向外传播，不用通用 finally 顺手修复别处寿命。

外层把宿主返回值翻译成 `.d.ts` 中的原生标签，提供具体消息、持久化动作和诊断格式；这里不解释宿主事件或重造请求。恢复仍沿现有认领规则：只凭精确物理消息认领结果，未找到就保留待决。认领序号在登记时消费，明确放弃后的新派发使用新序号；运行结束清理运行范围，未进入运行的会话根认领不被误清。

局部差分在 `tests/`；`attempt.test.mjs` 关注发送与确认的合作、异常清理和迟到时序。安装消费者在 `scripts/tests/package.test.mjs` 的 DispatchAttempt 项。实际执行结果由对应工作包记录，不在规则里维护通过状态。
