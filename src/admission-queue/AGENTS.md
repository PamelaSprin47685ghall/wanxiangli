# admission-queue

层：账本。执行准入等待队列的唯一 owner；不得 import 宿主 SDK，不选模型、不签发许可、不持有容量账本、不完成调用方的等待者、不计数。npm 入口 `wanxiangli/admission-queue`。

# AXIOM

1. [使用者] 容量不足时等待中的执行按到达先后公平地得到容量；同一次执行不排两次队，被替代或取消的执行不再占位。
    - 理由：插队或重复排队会让用户在 `wanxiangshu.mjs` 设下的并发上限变成某个会话独占；残留的等待会卡住后续执行。

# LEMMA

1. [本模块 AXIOM 1] 每个会话至多一个等待需求；同会话同物理用户消息再次入队是同一逻辑操作，交还原 node；同会话更新的物理消息替代旧需求，新需求排到队尾。
    - 推理：同一请求占两次队、旧 snapshot 在新物理执行生效都是 execution-model-routing 的反例。
2. [本模块 AXIOM 1] 等待需求有界（默认 32）；新会话在队满时被拒绝，不挤掉别人。
    - 推理：无界等待会把背压变成内存泄漏；挤掉已排队者破坏先到先得。
3. [本模块 AXIOM 1] 只有本队列签发、仍为该会话当前需求的 node 能被认领；同形对象或已被替代的旧 node 一律不认。
    - 推理：迟到的回调不能把容量交给一个已不存在的等待。
4. [本模块 AXIOM 1] 撤回只作用于该会话当前需求；给了物理消息时必须一致，否则视为迟到（StaleFence）且不改状态。
    - 推理：取消别人的执行、旧取消误伤新执行都是反例。

# SPEC

1. [LEMMA 1] 同物理消息 Reused；新物理消息 Queued 并交还 superseded；FIFO 序号单调。
    - 证明：`tests/001.test.mjs`。
2. [LEMMA 2] 队满时新会话 Full，已排队会话换物理世代仍可入队。
    - 证明：`tests/001.test.mjs`。
3. [LEMMA 3] null、伪造、被替代、已认领的 node 认领失败且不改状态。
    - 证明：`tests/001.test.mjs`。
4. [LEMMA 4] 撤回的三种结果；drain 按序交还全部 node 并清空。
    - 证明：`tests/001.test.mjs`。
