# capacity — 容量快照核对

层：内核纯计算。独立 npm 入口 `wanxiangli/capacity`。在总流程中，本模块只做一件事：拿调用方递来的一份容量快照，回答这几张账是否对得上；对不上就按固定次序把所有对不上的地方列出来。要不要因此收手，由外层决定。

[程序待改] 这类运行时检查员默认是待删债务：容量的一致性本该由 borrowing 与 permit 各自的写入路径守住，不必每次调度再核对一遍。现在保留，是因为外层的调度答复还在读 `FailClosed` 这个结果。使用方与解除条件登记在根《例外清单》：外层不再依赖它就删本入口。

## 状态所有权
- 无状态纯函数：不持有账本，不修改状态，不停止进程，不代替调用方做决定。
- 快照由调用方构造；本模块不读取 borrowing / permit 的内部字典，自己也不另存一份占用记录。

## AXIOM
1. [使用者] 并发不能超过用户设定的上限，等待者不能永久饿死；credit、令牌、托管、执行、等待者说的是同一份占用，它们彼此对不上，说明确实有人在错记账。
    - 理由：按错账继续调度会超发并发，把用户的钱与响应时间赔进去。

## LEMMA
1. [AXIOM 1] 单次读取一份一致快照，答案只有两种：`NoOp`（对得上）或 `FailClosed`（附全部对不上的项），不做静默修复。
2. [AXIOM 1] 七类不一致独立判定、按固定次序全部报告：活跃数越界、令牌状态计数不符、账本与令牌 credit 分叉、令牌 owner 不可追溯、等待者 owner 不可追溯、执行无托管、计数器回退。
3. [AXIOM 1] 快照形状不合法直接抛错：形状错既不是「对上了」，也不属于那七类。

## SPEC（调用方流程）

1. **一次快照核对**：
   - 外层在自认为合适的时机构造快照调用 `decide(evidence)`；七条都对得上返回 `NoOp`。
   - 有对不上的项返回 `FailClosed`，附带固定次序的完整列表；本模块到此为止，继续调度、拒绝起新执行还是报错给用户，由调用方定。
   - 快照缺字段或类型不对时调用直接抛错，调用方按自己的配置错误处理，不当成「容量正常」。
